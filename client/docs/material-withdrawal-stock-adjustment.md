# แนวทางแก้ไขและยกเลิกใบเบิกวัสดุที่กระทบสต็อก

สถานะ: พัฒนา API และหน้าเว็บแล้ว — EF migration ใช้กับฐานข้อมูลท้องถิ่น `AssetFlow` แล้ว ยังต้องทดสอบขั้นตอนจริงผ่านหน้าเว็บก่อนใช้งานจริง

## สิ่งที่พัฒนาแล้ว

- เพิ่ม API ดูผลกระทบและประวัติ (`GET /api/MaterialWithdrawal/{id}/impact`, `GET /api/MaterialWithdrawal/{id}/revisions`)
- เพิ่ม API ปรับจำนวนและยกเลิก (`POST /api/MaterialWithdrawal/{id}/adjust`, `POST /api/MaterialWithdrawal/{id}/cancel`) โดยต้องระบุเหตุผล และบันทึกผลต่างเป็น stock cards เพิ่มเติม ไม่ลบรายการเดิม
- ตรวจยอดคงเหลือของต้นทางและปลายทางภายใน transaction เดียว พร้อมคำนวณยอด stock cards และยอดสรุปใหม่
- ยกเลิกใบเบิกไม่ได้เมื่อพบรายการเบิกหรือโอนต่อที่ปลายทาง; การปรับจำนวนยังทำได้เมื่อยอดใหม่ผ่านการตรวจสต็อก เช่น 10 → 9 หลังเบิกต่อ 8 แต่ 10 → 7 จะถูกปฏิเสธ
- เพิ่มหน้าปรับปรุงใบเบิกพร้อมจำนวนต่ำสุดเบื้องต้น เหตุผล ปุ่มยกเลิก และประวัติการเปลี่ยนแปลง

ข้อจำกัดของรุ่นนี้: ปรับได้เฉพาะจำนวนของวัสดุที่อยู่ในใบเดิม ไม่เปลี่ยนผู้เบิก/หน่วยงานปลายทางหรือเพิ่มชนิดวัสดุใหม่ การแสดงจำนวนต่ำสุดเป็นเพียงตัวช่วย; API ตรวจยอดจริงอีกครั้งเมื่อบันทึก ยังไม่ได้ทดสอบกับฐานข้อมูลจริงในกรณีแข่งขันกันของผู้ใช้สองคน

## ขอบเขตและตัวอย่าง

ใบเบิกวัสดุในระบบอาจเป็นการย้ายวัสดุจากหน่วยงานต้นทางไปยังหน่วยงานของผู้เบิก ระบบบันทึก `OUT` ที่ต้นทาง และ `IN` ที่ปลายทางเมื่อเป็นคนละหน่วยงาน หลังจากนั้นปลายทางอาจมีรายการเบิกใช้หรือโอนต่อ

ตัวอย่าง: โอนโน้ตบุ๊ก 10 ตัวเข้าสาขาวิทยาการคอม สาขาเบิกใช้ต่อ 8 ตัว จึงเหลือ 2 ตัว หากแก้ใบโอนเดิมให้เหลือ 7 ตัวโดยไม่ตรวจรายการภายหลัง ยอดปลายทางจะเป็น 7 − 8 = −1 ตัว และยอดต้นทางจะเพิ่ม 3 ตัวอย่างไม่ถูกต้องตามลำดับเหตุการณ์

## กติกาธุรกิจที่เสนอ

1. แยกการแก้ข้อมูลเอกสารที่ไม่กระทบยอด เช่น หมายเหตุ ออกจากการแก้จำนวน รายการวัสดุ หรือหน่วยงานปลายทาง
2. ก่อนเปลี่ยนรายการที่กระทบยอด ให้ตรวจรายการสต็อกทั้งหมดที่เกิดภายหลังในทุกหน่วยงานและวัสดุที่เกี่ยวข้อง **ตามลำดับเวลา** ยอดระหว่างทางและยอดสุดท้ายต้องไม่ติดลบ
3. หากมีรายการเบิกหรือโอนต่อจนการแก้ไขทำให้ยอดช่วงใดติดลบ ให้ปฏิเสธ พร้อมแสดงวัสดุ หน่วยงาน ยอดที่ขาด และรายการที่เกี่ยวข้อง ผู้ใช้ต้องแก้รายการภายหลังตามข้อเท็จจริงก่อน
4. การลดจำนวนโอนจาก 10 เหลือ 7 ในตัวอย่างต้องถูกปฏิเสธ เพราะมีการเบิกต่อแล้ว 8 ตัว แต่การโอนใหม่ตั้งแต่ 8 ตัวขึ้นไปเป็นเพียง **เงื่อนไขเบื้องต้น** ยังต้องผ่านการตรวจยอดและลำดับเวลาทั้งหมด
5. เมื่อใบเบิกตัดสต็อกแล้ว การยกเลิกต้องเป็นการกลับรายการสต็อกที่อ้างอิงใบเดิม ไม่ใช่ลบใบหรือปิด `is_active` ของรายการเดิมจนประวัติหาย ต้องบันทึกเหตุผล ผู้ดำเนินการ และเวลา
6. ถ้ามีการใช้หรือโอนต่อจนคืนยอดทั้งหมดไม่ได้ ให้ปฏิเสธการยกเลิก ผู้ใช้ต้องจัดการรายการปลายทางก่อน หรือทำรายการคืนบางส่วนตามกระบวนการที่กำหนดแยกต่างหาก
7. ทุกการตรวจและบันทึกยอดต้องอยู่ใน transaction เดียว ฝั่ง API ต้องตรวจซ้ำเสมอ แม้หน้าเว็บจะตรวจและแสดงข้อจำกัดไว้แล้ว

## พฤติกรรมหน้าเว็บที่เสนอ

- แสดงสถานะใบเบิก: ยังไม่ตัดสต็อก, ตัดสต็อกแล้ว, ยกเลิกแล้ว
- หน้ารายละเอียดแสดงต้นทาง ปลายทาง จำนวนที่โอน จำนวนที่มีรายการภายหลัง และประวัติปรับปรุง
- การแก้หมายเหตุหรือข้อมูลที่ไม่กระทบยอดใช้ขั้นตอนสั้นได้ การแก้จำนวน/วัสดุ/ปลายทางใช้ปุ่ม **ปรับปรุงใบเบิก** พร้อมตัวอย่างยอดก่อนและหลังและช่องระบุเหตุผล
- ปุ่ม **ยกเลิกใบเบิก** ให้แสดงผลกระทบต่อยอดทุกหน่วยงานก่อนยืนยัน หากมีรายการภายหลังที่ทำให้ยกเลิกไม่ได้ ให้แสดงเหตุผลและรายการที่ต้องตรวจ
- ไม่ใช้คำว่า **ลบ** กับใบเบิกที่มีประวัติสต็อกแล้ว

## แนวทาง API และข้อมูล

1. เพิ่มข้อมูลสำหรับ preview ผลกระทบของการปรับปรุง/ยกเลิก โดยอ่านรายการสต็อกที่อ้างอิงใบเบิกและรายการที่เกิดตามมา ส่งยอดก่อน–หลังและสาเหตุที่บันทึกไม่ได้ให้หน้าเว็บ
2. เพิ่มคำสั่งปรับปรุงและยกเลิกที่รับเหตุผลและตรวจเงื่อนไขเดิมอีกครั้งภายใน transaction ที่ป้องกันการแก้พร้อมกัน
3. เก็บรายการสต็อกเดิมไว้ และเพิ่มรายการกลับยอด/ชดเชยที่เชื่อมกับใบเบิกและรายการต้นฉบับ กำหนดเวลาและลำดับรายการให้ชัดเจนเพื่อคำนวณย้อนหลังได้
4. บันทึกสถานะใบเบิก ผู้ดำเนินการ เวลา เหตุผล และความเชื่อมโยงของรายการปรับปรุง/ยกเลิก เพื่อใช้ตรวจสอบย้อนหลัง
5. คำนวณยอดคงเหลือรายวัสดุและรายหน่วยงานใหม่จากรายการสต็อกที่มีผลจริง และทำให้ยอดสรุปใน `MaterialItem` ตรงกับ stock cards

## จุดที่ต้องตรวจในโค้ดก่อนลงมือ

- `backend/APi/Controllers/Materials/MaterialWithdrawalItemsController.cs`: `PUT /{withdrawalId}/with-items` ปัจจุบันปิด stock cards เดิม แล้วสร้าง cards ใหม่ด้วยเวลาปัจจุบัน จากนั้นคำนวณยอดใหม่และปฏิเสธยอดติดลบ ต้องกำหนดวิธีรักษาลำดับและประวัติรายการให้ชัดก่อนเปิดให้แก้รายการที่มีการเบิกต่อ
- `backend/APi/Controllers/Materials/MaterialWithdrawalController.cs`: `DELETE /{id}` ปัจจุบันตอบ `409 Conflict` เมื่อมี stock card ที่ยัง active จึงยังไม่ใช่ขั้นตอนยกเลิกพร้อมคืนยอด
- `client/src/app/features/materialWithdrawal/`: ตรวจเส้นทางหน้ารายการและหน้ารายละเอียด แล้วออกแบบปุ่ม/ข้อความตามสถานะจาก API
- ตรวจรายการเบิกภายในจาก `MaterialIssueDetailController` และการปรับ stock card ทางอื่น เพื่อให้การตรวจ dependency ครอบคลุมทุกเส้นทาง

## ลำดับงานเมื่อเริ่มพัฒนา

1. สรุปนิยามสถานะใบเบิกและสิทธิ์ผู้แก้/ยกเลิก รวมถึงกรณีคืนบางส่วน
2. เพิ่มโครงสร้างประวัติและรายการกลับยอด พร้อม migration
3. ทำ API preview และ API บันทึก โดยตรวจลำดับยอดทุกจุดและการแก้พร้อมกัน
4. ปรับหน้าเว็บให้แสดงผลกระทบ เหตุผล และข้อความปฏิเสธที่ระบุรายการปัญหา
5. ทดสอบกรณีโอน 10 → เบิกต่อ 8 → ขอแก้เป็น 7 (ต้องปฏิเสธ), แก้เป็น 9 (พิจารณาตามลำดับรายการ), ยกเลิกหลังเบิกต่อ (ต้องปฏิเสธ), ยกเลิกก่อนเบิกต่อ (ยอดคืนถูกต้อง), และผู้ใช้สองคนแก้พร้อมกัน

เอกสารนี้เป็นแนวทางออกแบบ ยังต้องยืนยันกระบวนการทางพัสดุและสิทธิ์ผู้ใช้งานก่อนลงมือพัฒนา
